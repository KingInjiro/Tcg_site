# Редагування та публікація з браузера

Батькові не потрібні Node.js, Git або ZIP-архіви на комп’ютері. Після одноразового
налаштування він відкриває адресу редактора, входить через GitHub, редагує сторінки
та натискає **Опублікувати**. Дизайн і вміст публічних сторінок ця інтеграція не змінює.

## Де що працює

- **Сайт для відвідувачів** може залишатися на звичайному статичному хостингу.
- **Адмінпанель і поштовий API** працюють окремо, наприклад на наявному Vercel.
  Сам статичний хостинг не виконує `/api/auth`, `/api/callback`, `/api/contact`
  або `/api/mail-status`. Адресою редактора буде `https://АДРЕСА-НА-VERCEL/admin/`.
- **GitHub** зберігає сторінки, перевіряє їх і передає готові публічні файли
  на хостинг через SFTP або FTPS. Це виконується на сервері GitHub.

Потрібні GitHub-акаунт із правом запису в `KingInjiro/Tcg_site`, увімкнені Actions
та налаштований OAuth-вхід за [інструкцією README](../README.md#налаштування-входу).
Без можливості SFTP/FTPS або іншого API на хостингу автоматична передача туди
неможлива: тоді потрібен ручний експорт або інший спосіб розгортання.

## Що відбувається після натискання кнопки

1. Редактор зберігає сторінки, дані конструктора й нові картинки одним комітом
   в окрему гілку `cms/...`. Поточний сайт у цей момент не змінюється.
2. GitHub Actions → **Site checks** перевіряє HTML5, кодування, локальні ресурси,
   декодування картинок, внутрішні посилання та якорі. Для правок конструктора
   не порівнюється старий і новий текст: власник має право змінювати вміст.
   Для PR зі змінами коду зберігається повний набір тестів.
3. Лише після успіху **Publish checked site** повторно перевіряє результат
   для конкретного коміту, дозволені файли та відсутність чужих змін у `main`.
   У `main` потрапляє саме перевірений коміт, без примусового перезапису історії.
4. Якщо налаштовано статичний хостинг, workflow створює публічний експорт і
   завантажує його. Спочатку ресурси, потім HTML, останнім — `sw.js`.
5. Редактор показує стан і посилання на журнал. Браузер можна закрити після
   повідомлення про збереження чернетки: перевірки та передача продовжаться.

До завершення поточної перевірки повторна публікація недоступна; редагування
та резервна копія доступні. Номер коміту чернетки зберігається в браузері,
GitHub-токен — лише в пам’яті вкладки. Після повторного входу в тому самому
браузері редактор відновить відправлену чернетку й покаже її стан. Незбережені
правки, зроблені вже після відправлення, треба зберегти резервною копією.
При очищенні браузерного сховища гілка `cms/...` залишиться в GitHub, але
автоматичне відновлення її стану в редакторі буде втрачено.

**Без налаштувань хостингу** передача SFTP/FTPS вимкнена. Успіх workflow тоді
означає перевірку та оновлення `main`, а не підтверджену появу сторінок у Vercel.
Наявна Git-інтеграція Vercel має окремий стан розгортання: перевіряйте
Vercel → Deployments. Для звичайного хостингу виконайте наступний розділ.

## Одноразово підключити звичайний хостинг

Спершу зробіть резервну копію поточного сайту засобами хостингу. Запитайте
у підтримки хостингу:

> Чи можна завантажувати файли сайту через SFTP із SSH-ключем або через FTPS
> з обов’язковим TLS? Потрібні адреса сервера, порт, логін, окрема папка цього
> сайту та спосіб створити окремі облікові дані для завантаження. Для SFTP також
> потрібен підтверджений відкритий ключ сервера / його fingerprint. Чи дозволено
> підключення з GitHub Actions?

Звичайний незашифрований FTP і SFTP лише з паролем ця реалізація не використовує.
Підтримуються SFTP з ключем і explicit FTPS (`AUTH TLS`, зазвичай порт 21).
Не обирайте кореневу папку всього облікового запису; потрібна папка саме сайту.

У GitHub → репозиторій → **Settings → Environments → New environment** створіть
`site-publishing`. За потреби обмежте deployment branches гілкою `main`:
workflow публікації запускається з довіреної основної гілки. Якщо налаштувати
required reviewers, публікація чекатиме їхнього схвалення.

У цьому environment додайте **Variables**:

| Назва | Значення |
| --- | --- |
| `STATIC_DEPLOY_ENABLED` | Спочатку `false`; після внесення та перевірки всіх даних — `true` |
| `STATIC_PROTOCOL` | `sftp` або `ftps` |
| `STATIC_HOST` | Ім’я сервера без `https://` та без шляху |
| `STATIC_PORT` | Порт від хостингу; типово 22 для SFTP або 21 для FTPS |
| `STATIC_DIRECTORY` | Папка сайту, наприклад `/public_html`; шлях уточнити у підтримки |
| `CONTACT_FORM_ENDPOINT` | Повна HTTPS-адреса окремого API, наприклад `https://АДРЕСА-НА-VERCEL/api/contact` |

Абсолютний шлях починається з `/`; відносний рахується від домашньої папки
облікового запису. Корінь `/` заборонений. На хостингу з ізоляцією облікового
запису шлях рахується всередині цієї ізоляції.

У тому самому environment додайте **Secrets**:

| Назва | Для чого |
| --- | --- |
| `STATIC_USER` | Логін окремого користувача завантаження |
| `STATIC_SSH_KEY` | Лише SFTP: приватний SSH-ключ; відповідний публічний ключ додайте на хостингу |
| `STATIC_KNOWN_HOSTS` | Лише SFTP: запис відомого ключа сервера у форматі OpenSSH `known_hosts`, підтверджений хостингом |
| `STATIC_PASSWORD` | Лише FTPS: пароль користувача завантаження |

Не записуйте ключі й паролі у файли репозиторію або повідомлення. Вміст ключа
потрібно вставляти з оригінальними переносами рядків. Для нестандартного SFTP-порту
запис known_hosts використовує `[ім’я-сервера]:порт`. Не вимикайте перевірку ключа
або TLS-сертифіката при помилці: звірте налаштування з підтримкою.

Workflow просить тільки необхідні права GitHub: читання перевірок, запис вмісту
та статусів. Організаційна політика або захист `main` можуть забороняти пряме
оновлення навіть після перевірок; у такому випадку автоматична публікація зупиниться.
Не вимикайте весь захист навмання: адміністратор має погодити дозволений спосіб
оновлення цієї гілки. Власні PR можна продовжувати зливати звичайним способом.

Після налаштування натисніть **Опублікувати** для реальної потрібної правки.
Перевірте **Site checks**, потім **Publish checked site**, а потім відкрийте
сам публічний сайт. Для першої перевірки можна вказати окрему тестову папку
і тестовий домен, щоб не торкатися робочого сайту.

## Якщо щось не пройшло

- **Помилка HTML, картинок або посилань:** відкрити журнал **Site checks**,
  виправити правку в редакторі й опублікувати знову. Чернетка не зникає.
- **Main changed during checks:** хтось уже змінив сайт. Зробіть резервну
  копію чернетки. Для відкриття свіжого `main` очистіть лише ключ
  `tcg-publication` у сховищі цього сайту (DevTools → Application → Local Storage),
  увійдіть заново й перенесіть потрібні правки вручну. Не імпортуйте поверх
  чужих змін цілий старий сайт без порівняння.
- **Збій з’єднання з хостингом:** виправити налаштування, у GitHub Actions
  відкрити відповідний **Publish checked site** → **Re-run failed jobs**.
  Повторення допускається, поки цей коміт залишається актуальним `main`.
- **Публікація чекає:** перевірити, чи не потрібне схвалення environment,
  чи увімкнені Actions та чи не вичерпано ліміт GitHub.

Файли передаються під тимчасовими назвами й потім перейменовуються. Це захищає
окремий файл від неповного завантаження, але **не є атомарною заміною всього сайту**.
При обриві частина файлів уже може оновитися. Повторіть передачу перевіреної
версії або відновіть резервну копію хостингу. Сторонні й старі файли workflow
не видаляє; автоматичне видалення сторінок у конструкторі не передбачено.
Службові файли, вихідний код backend, токени та адмінпанель у статичний експорт
не включаються. Папка сайту не повинна містити встановлену CMS із файлами,
які збігаються за іменами з публічними файлами цього проєкту.

## Пошта: налаштування й чесна перевірка

На сервері, де працює `/api/contact`, задайте `SMTP_HOST`, `SMTP_PORT` (465 або
587), `SMTP_USER`, `SMTP_PASSWORD`, `CONTACT_FROM`, `CONTACT_TO`, постійний
`CONTACT_TOKEN_SECRET`. Для окремого статичного домену додайте його повний
origin до `CONTACT_ALLOWED_ORIGINS`, наприклад `https://www.tcg.com.ua`.
Декілька origin можна перелічити через кому; `http`, `https`, домен з `www`
і без нього — різні origin. Деталі є в розділі README про форми та SMTP.
Зміни серверних змінних Vercel потребують нового розгортання.

В онлайн-адмінпанелі кнопка **Перевірити пошту**:

1. Перевіряє через GitHub право запису цього адміністратора в репозиторій.
2. Показує назви відсутніх/некоректних налаштувань, без їхніх значень.
3. Перевіряє TLS і вхід на SMTP-сервер. Листів не надсилає.

Позитивна перевірка **не підтверджує доставку**. Для остаточної перевірки
власник сам надсилає одне тестове звернення через публічну форму з власною
адресою та перевіряє отримання в `CONTACT_TO`, включно зі спамом. При проблемі
перевіряє журнали поштового провайдера та його налаштування відправника/SPF/DKIM.
Без реальних налаштувань пошти і доступу до скриньки заявляти про доставку не можна.

## Технічна межа перевірок

Автотести перевіряють захист публікації, конфлікти, відновлення стану, авторизацію
поштової діагностики та формування захищеної передачі. Вони не використовують
робочі паролі й не надсилають листів. Підтримку протоколу, права папки, DNS,
сертифікат і приймання пошти на конкретному хостингу треба перевірити після
підключення цього хостингу. GitHub Actions має власні ліміти використання.
