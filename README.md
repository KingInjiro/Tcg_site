# TCG — сайт із візуальним конструктором

Сайт можна редагувати без програмування: змінювати текст прямо на сторінці,
додавати картинки та створювати нові сторінки. Оригінальне оформлення, GIF-меню
та жовте підсвічування при наведенні збережені.

**Для звичайного або невідомого хостингу використовуйте локальний режим:**
конструктор працює на комп’ютері, а на хостинг ви завантажуєте готовий ZIP.
Для цього режиму не потрібні GitHub-акаунт, Vercel, Client ID або Client Secret.
Node.js потрібен лише на комп’ютері редактора; на хостингу достатньо можливості
розмістити звичайні HTML, CSS, JavaScript, зображення та документи.

**Збереження на комп’ютері не оновлює сайт в інтернеті.** Оновлення з’явиться для
відвідувачів після завантаження та розпакування архіву на хостингу.
Онлайн-редактор із GitHub також залишився — його окремі налаштування наведені нижче.

Сторінки переведені на HTML5 зі збереженням поточного оформлення й вмісту.
У робочому проєкті файли залишаються `.html`, щоб конструктор зберігав їх як раніше;
після збірки, експорту й у локальному перегляді адреси не містять цього закінчення.
Налаштування конструктора й адреса `/api/callback` не змінюються.

Основна іконка вкладки браузера — оригінальний анімований
`images/tcg_log3.gif`. Резервні варіанти — його статичний перший кадр:
`images/favicon-32.png` і `favicon.ico` (16, 32 і 48 px).
Браузер сам вибирає підтримуваний формат. Якщо він читає GIF, але не
анімує іконки вкладок, може показати перший кадр GIF; це також статичний
логотип. Якщо GIF-формат не підходить, доступні PNG та ICO. Визначати
підтримку анімації за назвою браузера чи примусово перемикати кадри скриптом
не потрібно. Усі варіанти автоматично підключаються до сторінок, зокрема
нових сторінок конструктора, при збірці й експорті та доступні офлайн.
Завантажуйте `favicon.ico` та папку `images` разом з іншими файлами сайту.

## Телефони, планшети та різні екрани

Сайт підлаштовується під ширину вікна. До 900 px меню розташовується над
вмістом, а поля контактних форм — під підписами. Зони натискання кнопок меню
та полів збільшені для вузьких екранів і сенсорних пристроїв; оригінальні
GIF-кнопки та їх підсвічування збережені. Підписи прапорців також натискаються.

Широкі прайси й таблиці витрат прокручуються вбік усередині свого блока;
текст навколо них залишається в межах екрана. Для прокручування клавіатурою
перейдіть до таблиці клавішею Tab і використайте стрілки. Масштабування
сторінки браузером доступне, адаптація не потребує JavaScript.

`npm run test:responsive` перевіряє всі 51 сторінку в Chromium на ширинах
320, 390, 768, 900, 1024, 1440, 1920 та 2560 px, а також сенсорні переходи,
поворот екрана, пошук і форми. У CI основні типи сторінок додатково проходять
цю перевірку у Firefox і WebKit. Це браузерна емуляція розмірів і сенсорного
введення; перевірка на фізичних пристроях не входить до автоматичного тесту.

## SPA та встановлення PWA

У готовій збірці внутрішні переходи працюють як SPA: сторінка, її заголовок
і адреса оновлюються без перезавантаження всього документа. Працюють
«назад/вперед», відновлення прокручування, пошук, форми та калькулятори.
Кожна адреса водночас залишається справжньою HTML-сторінкою: її можна відкрити
напряму, перезавантажити чи використати без JavaScript. Завантаження документів,
зовнішні посилання, нова вкладка й адмінка використовують звичайну навігацію.
Сторінки з доданими власноруч невідомими скриптами також відкриваються звичайно.

**Для встановлення як застосунку сайт має працювати через HTTPS.** Виняток —
локальний перегляд через `localhost` / `127.0.0.1`. На звичайному HTTP-хостингу
сам сайт і переходи працюють, але PWA не встановлюється.

1. Відкрийте сайт онлайн у браузері з підтримкою встановлення вебзастосунків.
2. Скористайтеся значком встановлення біля адреси або командою встановлення
   в меню браузера. На iPhone — меню «Поділитися» → «На початковий екран».
   Назва й наявність команди залежать від браузера та операційної системи.
3. Після успішного першого завантаження офлайн-кешу можна відкривати збережені
   сторінки, зображення, меню, пошук і калькулятор резервних копій без інтернету.
   Архіви/документи для завантаження, сторонні сайти, свіжі курси, новини та
   надсилання форм потребують мережі. Форми не ставляться в приховану чергу.

Маніфест підключається до всіх сторінок при збірці й експорті. Іконка застосунку
використовує наявний логотип, самі сторінки не перемальовані. Офлайн-кеш включає
всі публічні сторінки та локальні стилі, скрипти й картинки; нові сторінки
конструктора включаються при наступному експорті/збірці. Адмінка, API, токени
та введені у форми дані в цей кеш не записуються.

Готові публічні сторінки, стилі й зображення відкриваються з кешу поточної
версії без очікування мережі на кожному переході. Курси, новини, надсилання
форм та інші запити до API працюють через мережу. Спільні CSS-файли при
SPA-переходах використовуються повторно; нові стилі, скрипти й основні
зображення готуються паралельно. Поки перехід триває, тонка смужка вгорі
та курсор показують, що натискання прийняте.

Після оновлення сайту новий кеш завантажується у фоні. Він активується після
закриття старих вкладок/вікон застосунку; примусового перезавантаження форми немає.
Браузер може очистити офлайн-дані за браку місця або після ручного очищення.
Весь вміст ZIP потрібно завантажувати на хостинг разом, включно з `sw.js`,
`manifest.json`, `images` та `themes`.

Технічні вимоги й відмінності браузерів:
[MDN: встановлення PWA](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

## Що передати батькові

1. Після додавання цих змін у `main` відкрийте
   [репозиторій Tcg_site](https://github.com/KingInjiro/Tcg_site).
2. Натисніть зелену кнопку **Code → Download ZIP**. Передайте отриманий
   `Tcg_site-main.zip` батькові. Це **проєкт із конструктором**, а не архів для хостингу.
3. Батько розпаковує його у постійну папку на своєму комп’ютері й виконує наступні
   кроки. Файл `README.md` усередині — ця сама інструкція; її зручно читати на GitHub.
4. Якщо ви вже редагували сайт **локально**, передавайте свою актуальну робочу
   папку за інструкцією «Резервні копії» нижче. ZIP із GitHub не містить локальних правок.

## Перший запуск на Windows

1. Відкрийте [офіційне завантаження Node.js](https://nodejs.org/en/download).
   Виберіть **версію 24 LTS**, систему **Windows** та інсталятор **Windows Installer (.msi)**.
   Встановіть зі звичайними параметрами; npm встановлюється разом із Node.js.
   Якщо Node.js 24 уже встановлений, повторювати цей крок не потрібно.
2. У Провіднику натисніть правою кнопкою на `Tcg_site-main.zip` → **Видобути все**.
   Наприклад, збережіть проєкт у `Документи/TCG`. Відкрийте папку, де поруч лежать
   `START-EDITOR.cmd`, `package.json` та `index.html`. Не запускайте редактор усередині ZIP.
3. Двічі натисніть **START-EDITOR.cmd**. Якщо Провідник приховує розширення,
   він може показувати назву `START-EDITOR` із типом «Сценарій команд Windows».
4. Під час першого запуску потрібен інтернет: програма сама встановить компоненти.
   Дочекайтеся повідомлення **«Редактор готовий»**. Після оновлення проєкту або Node.js
   компоненти можуть перевстановитися. Наступні запуски використовують установлену копію.
5. Відкриється браузер. Натисніть **Відкрити редактор**. Якщо браузер не відкрився,
   скопіюйте адресу після «Редактор готовий» у його адресний рядок. Вона виглядає як
   `http://127.0.0.1:ЧИСЛО/admin/?local=true`; число програма вибирає автоматично.
6. **Залишайте вікно запуску відкритим**, доки працюєте. Щоб завершити, збережіть
   правки в редакторі та закрийте вікно запуску або натисніть у ньому `Ctrl+C`.

Надалі запускайте той самий `START-EDITOR.cmd` у тій самій папці.
Адреса редактора може змінюватися при кожному запуску. Вона відкривається лише
на цьому комп’ютері; її не потрібно додавати в налаштування домену чи хостингу.
Не видаляйте робочу папку після публікації сайту.

### macOS та Linux

Установіть **Node.js 24** з офіційного сайту, розпакуйте проєкт і відкрийте термінал
у папці з `package.json`. Виконайте:

```sh
sh START-EDITOR.command
```

Або на будь-якій системі, де доступні Node.js 24 і npm:

```sh
npm run editor
```

Обидва способи самі встановлюють компоненти при першому запуску, готують редактор
та відкривають браузер. Залишайте термінал відкритим. Для запуску без автоматичного
відкриття браузера: `npm run editor -- --no-open`.

## Редагування та нові сторінки

1. Виберіть сторінку ліворуч. Пошук знаходить її за назвою або адресою.
2. Двічі натисніть на текст, щоб переписати його. Перетягніть готовий блок із лівої
   панелі або натисніть на блок, щоб додати його до вибраного елемента чи в кінець сторінки.
3. Виберіть елемент: праворуч доступні шрифт, колір, розмір, відступи та рамка.
   Для картинки натисніть **Вибрати зображення → Завантажити** й виберіть файл
   PNG, JPG, GIF або WebP до 2 МБ. Зображення збережеться разом зі сторінками.
4. Кнопка **+** біля «Сторінки» створює нову сторінку. Вкажіть назву та адресу
   латиницею, наприклад `nashi-posluhy` → `/nashi-posluhy/`.
   **Щоб зберегти оформлення старого сайту, виберіть «Копія поточної сторінки»**
   й замініть її вміст. Також є простий шаблон і шаблон послуг.
5. Позначка **Додати посилання внизу поточної сторінки** робить нову сторінку
   доступною з тієї, яку ви відкрили перед створенням. Оригінальні GIF-меню
   автоматично не перемальовуються. Для додаткового переходу виберіть посилання
   в редакторі та його ціль у списку **Посилання на сторінку** праворуч.
6. Перевірте **Перегляд** і вигляд на телефоні. Стрілки над полотном скасовують
   або повторюють дію. Щоб перевірити вже збережений сайт зі скриптами, натисніть
   логотип **TCG** у верхньому лівому куті — він відкриє локальний сайт у новій вкладці.
7. Натисніть **Зберегти на комп’ютері**. Зберігаються всі змінені сторінки та нові
   зображення. Після повідомлення «Збережено» можна закрити редактор і повернутися пізніше.

Зайнята адреса не перезаписується при створенні нової сторінки. Видалення сторінок
і зміна адреси вже створеної сторінки в інтерфейсі не передбачені.
Чернетки до збереження перебувають лише у відкритій вкладці.
Одна операція збереження обмежена 100 файлами та 8 МБ даних, включно з даними
блоків і кодуванням зображень. Зберігайте великі зміни частинами.

## Як завантажити сайт на будь-який звичайний хостинг

### Створіть архів

1. У конструкторі натисніть **Архів для хостингу**.
2. Кнопка спочатку збереже всі поточні правки, потім збере ZIP. Якщо є конфлікт
   або помилка збереження, архів не буде завантажено — усуньте помилку за повідомленням.
3. Браузер завантажить `tcg-hosting-ДАТА-ЧАС.zip`. Друга копія є в папці **exports**
   усередині робочого проєкту. Використовуйте найновіший файл.

Архів містить готові сторінки, CSS, скрипти, картинки та документи; в його корені
лежить `index.html`. Він не містить конструктора, серверного коду, `.env`, Git-історії,
`node_modules` чи приватних даних блоків `.tcg-editor`.
Сторінки публікуються як папки з `index.html`: відвідувач бачить `/contacts/`,
а для головної — `/`. Старі `.html` і `.htm` ведуть на ці самі сторінки.
На звичайному статичному хостингу перенаправлення виконує браузер; у Node.js
і на Vercel — сервер. Завантажуйте весь архів разом із новими папками.
Службова HTML-сторінка для старої адреси документа 1С веде на `.ert`.

### Перше розміщення або оновлення

1. Увійдіть у панель хостингу з даними його власника. Назва провайдера не впливає
   на формат архіву; доступ до файлового менеджера або FTP/SFTP все одно потрібен.
2. **Зробіть і завантажте на комп’ютер резервну копію чинного сайту** засобами
   хостингу. Збережіть її до завершення перевірки нового сайту.
3. У налаштуваннях потрібного домену знайдіть його **кореневу папку / document root**.
   Поширені назви — `public_html`, `www`, `htdocs`, але назва сама по собі не є
   гарантією: у хостингу може бути кілька доменів із різними папками.
4. Відкрийте цю папку у файловому менеджері. Завантажте туди ZIP і виберіть
   **Розпакувати / Extract**, дозволивши заміну однойменних файлів.
5. Перевірте результат: **сам `index.html` має лежати безпосередньо в папці домену**,
   а поруч — `images`, `derived`, `themes`, `Docs`, `ListPage` та інші файли архіву.
   Не розміщуйте їх усередині додаткової папки `dist`, `Tcg_site-main` чи `exports`.
6. Якщо розпакування на хостингу немає, розпакуйте ZIP на комп’ютері та завантажте
   **весь його вміст**, зберігаючи вкладені папки й регістр літер, через файловий
   менеджер або вже налаштований FTP/SFTP-клієнт. Підтвердіть заміну однойменних файлів.
7. Відкрийте сайт за його звичайною адресою: перевірте головну, меню та підсвічування,
   змінену й нову сторінки, картинки та завантаження документів. На Windows `Ctrl+F5`
   оновлює сторінку без використання кешу браузера. Якщо хостинг має окремий кеш/CDN,
   очистьте його в панелі.
8. Після успішного розпакування видаліть завантажений ZIP **із хостингу**.
   Робочу папку проєкту й резервні копії на комп’ютері залиште.

Для наступного оновлення повторіть ці кроки з новим архівом. ZIP містить **повний
публічний сайт**, а не лише різницю. Не видаляйте сторонні файли хостингу навмання.
Якщо старий `index.php`, правила `.htaccess` або перенаправлення заважають показати
новий `index.html`, попросіть підтримку перевірити стартовий файл і папку саме цього
домену. Спочатку збережіть резервну копію цих налаштувань.

Цей варіант розрахований на **корінь домену або піддомену**, наприклад
`https://www.tcg.com.ua/`. Для адреси всередині папки на кшталт
`https://example.com/tcg/` потрібно окремо адаптувати абсолютні шляхи сайту.
При збереженні того самого домену змінювати DNS для простого завантаження файлів не потрібно.

На звичайному хостингу `/admin/` із цього архіву не встановлюється: для редагування
запускайте конструктор на комп’ютері. Автоматичного завантаження на FTP/SFTP в цьому
режимі немає. Два комп’ютери також не синхронізуються автоматично — передавайте
актуальну робочу папку й узгоджуйте, хто зараз редагує сайт.

| `tcg-hosting-…zip` | Завантажити готовий сайт на хостинг або повернути попередню публічну версію |
| **Копія чернетки** → JSON | Тимчасово зберегти лише незбережені правки з відкритої вкладки |
| Резервна копія з панелі хостингу | Відновити попередній стан чинного сайту та його налаштувань |

Для повної копії спочатку натисніть **Зберегти на комп’ютері**, закрийте редактор і
заархівуйте робочу папку. Можна не включати `node_modules`, `dist`, `exports` та `.git`:
вони не потрібні для передачі конструктора. **Залиште `.tcg-editor`, усі сторінки,
зображення, код конструктора, `package.json` та `package-lock.json`**. Якщо файл `.env`
було створено для онлайн-режиму, не включайте його із секретами в архів для передачі.
Локальному режиму він не потрібен.

На іншому комп’ютері встановіть Node.js 24, розпакуйте цю копію та запустіть
`START-EDITOR.cmd` або `sh START-EDITOR.command`. Нове завантаження проєкту з GitHub
не замінює таку копію: локальні правки в GitHub автоматично не відправляються.

JSON чернетки повертається через **Відновити**, якщо базова версія сайту відтоді
не змінилася. Він не містить усіх сторінок чи повного комплекту зображень.
Якщо інший редактор або інша вкладка змінили файли, збереження й експорт зупиняються
без перезапису цих змін. Збережіть чернетку, відкрийте актуальну версію та перенесіть
потрібні правки; автоматичне об’єднання конфліктних версій не виконується.

Для повернення попереднього стану хостингу використовуйте його резервну копію.
Старий ZIP замінить однойменні файли, але не видалить сторінки, додані пізніше.
Робочу папку конструктора відновлюйте з відповідної повної копії окремо.

## Якщо щось не працює

| Ситуація | Що зробити |
| --- | --- |
| «Потрібен Node.js 24» / `node` не знайдено | Встановити саме 24 LTS, закрити вікно запуску й відкрити `START-EDITOR.cmd` знову |
| Перше встановлення компонентів завершилося помилкою | Перевірити інтернет, вільне місце та текст помилки у вікні запуску; запустити ще раз |
| Браузер не відкрився | Скопіювати повну адресу після «Редактор готовий» із вікна запуску |
| Після закриття вікна запуску редактор недоступний | Запустити `START-EDITOR.cmd` знову; незбережені чернетки могли залишитися лише в старій вкладці |
| Пише «Сайт змінився» | Зберегти JSON чернетки, перечитати актуальний сайт і перенести правки; не намагатися примусово перезаписати іншу версію |
| ZIP не з’явився у завантаженнях браузера | Перевірити повідомлення редактора й папку `exports`; після успіху там також є копія |
| На хостингу старий сайт | Переконатися, що завантажено найновіший ZIP у папку правильного домену, файли замінено й кеш очищено |
| Є текст, але немає картинок або оформлення | Завантажити весь вміст ZIP зі збереженням регістру й папок; переконатися, що сайт розміщено в корені домену |
| На хостингу `/admin/` повертає 404 | У локальному режимі це очікувано: редагування запускається на комп’ютері |
| На іншому комп’ютері зникли правки | Передати актуальну робочу папку, а не повторно завантажений ZIP із GitHub |

Для перегляду готового сайту користуйтеся локальним сервером через логотип TCG або
адресою домену. Просте подвійне натискання на `index.html` відкриває `file://` і не
відтворює роботу сервера з абсолютними шляхами.

## Межі старого сайту та збереження оформлення

Пошук на `/search/` працює без FrontPage і без зовнішнього пошукового сервісу.
Індекс формується з актуальних збережених сторінок при збірці та експорті, включно
з новими сторінками конструктора. Для пошуку потрібен JavaScript; без нього є
посилання на оглавлення. Успадковані зовнішні пошукові блоки Google та META не повертаються.

Чотири форми (`/feedback/`, `/1CPrice/`, `/price01/`, `/price1C/`) тепер мають
спільний обробник `/api/contact`. Для реальної пошти необхідне налаштування SMTP
за інструкцією нижче. Сам статичний ZIP не є поштовим сервером: якщо обробника
немає або він відмовив, сайт показує помилку, зберігає введені дані й не повідомляє
про успішну відправку.

Зовнішні лічильники, новини та курси залежать від доступності своїх сервісів
та інтернету. Прибрані виклики недоступного `/pagead/f.txt`; інші зовнішні
інтеграції не підмінено вигаданими даними. Межі перевірок наведені в
[технічному звіті](docs/site-audit.md).

Наявні сторінки побудовані на старій табличній верстці. У редакторі можна
змінювати їхній вміст і структуру, але переміщення цілих вкладених таблиць змінює
макет: перевіряйте результат у перегляді. Перемикач телефона показує вузьке
вікно, а не автоматично перебудовує старий сайт в адаптивний дизайн.
Рекламні скрипти, форми та інші активні вставки не виконуються в полотні редактора;
наявні скрипти зберігаються при публікації. Для їх перевірки відкрийте живу сторінку.

Місце для банера розташоване у верхній частині наявних сторінок, поруч із логотипом
і над меню (`.site-banner` у таблиці `#table2`). Стилі задає `themes/banner.css`.
Порожній блок не має підпису, рамки чи власної висоти. Бокові рекламні заглушки,
які перекривали навігацію, прибрані; наявний код верхнього банера збережено.

`themes/layout.css` керує шириною наявних сторінок: головна використовує дві
колонки, прайси займають доступну ширину, текстові сторінки центровані та
обмежені за шириною. На вузьких екранах колонки складаються вертикально,
а широкі таблиці можна прокручувати всередині вмісту. Кольори, шрифти,
зображення меню та рамки залишаються у вихідній темі.

Меню використовує оригінальні GIF-кнопки: верхні службові — 90×25 px,
горизонтальні й бокові — 132×18 px, без масштабування написів. Для «Основная»
та «Вверх» у кожному ряду використано відповідний оригінальний варіант картинки.
`themes/navigation.css` при наведенні або фокусі клавіатури показує наявний
файл кнопки `*_A.GIF` із вихідним жовтим сяйвом. CSS не малює новий градієнт
і працює також у полотні конструктора, де виконання скриптів вимкнено.
Розташування верхніх переходів, заголовка й розділювальних ліній збережене.

Базовий розмір тексту — 16 px, дрібних підписів `.legacy-font[data-size="1"]` — 14 px.
Спільні правила усувають скидання шрифту таблиць і полів до браузерного стандарту
в старому режимі HTML. Зменшення `x-small` у новинах, тарифах, завантаженнях
та описі продукту замінені успадкуванням розміру; основний текст Word-прайсів
переведено з 10 pt на 16 px. Кольори, жирне й курсивне виділення збережені.

На головній у блоці курсів є конвертер USD/EUR/UAH. `themes/calculators.js`
запитує курс на поточну дату в Києві через [API НБУ](https://bank.gov.ua/ua/open-data/api-dev),
показує дату відповіді та рахує `сума × курс вихідної валюти / курс цільової`.
Курс UAH дорівнює 1. Відсутні, некоректні чи неактуальні дані блокують розрахунок;
кнопка оновлення повторює запит, тайм-аут — 10 секунд. Вбудованих запасних курсів немає.

На `ListPage/Pege05.html` калькулятор оцінює місце для повних резервних копій:
`обсяг однієї копії × кількість копій × (1 + запас / 100)` у ГБ.
Стиснення, дедуплікація та службові дані не враховуються; розрахунок локальний.
Обидва калькулятори приймають десяткову крапку або кому. У полотні конструктора
скрипти не запускаються; розрахунки працюють у перегляді опублікованої сторінки.


## Як увімкнути надсилання форм

Пошук, сторінки та конструктор не потребують цих налаштувань. Цей розділ потрібний
лише для отримання заявок на пошту. Відвідувачам не потрібен Node.js, Skype або
поштова програма: заявка надсилається з браузера на сервер.

### 1. Визначте, де працюватиме обробник

- **Сайт на Vercel:** `api/contact.js` уже є в проєкті. Задайте серверні змінні
  в Settings → Environment Variables й виконайте нове розгортання.
- **Сайт на Node.js-хостингу:** скопіюйте `.env.example` у `.env` у робочій папці
  проєкту, заповніть значення й запустіть `npm ci`, потім `npm start`.
  Публічний домен має працювати через HTTPS. Не публікуйте режим `--dev`.
- **Звичайний статичний хостинг:** сам ZIP не виконує `api/contact.js`.
  Обробник можна розмістити окремо на Vercel або Node.js-сервері, а сайт залишити
  на поточному хостингу. Налаштування двох адрес описані в пункті 3.

### 2. Задайте поштові налаштування на сервері обробника

Їх надає сервіс, де розміщена поштова скринька, а не GitHub OAuth App.

| Змінна | Що вписати |
| --- | --- |
| `SMTP_HOST` | Адреса SMTP-сервера від поштового провайдера |
| `SMTP_PORT` | `465` (TLS) або `587` (обов'язковий STARTTLS) |
| `SMTP_USER` | SMTP-логін |
| `SMTP_PASSWORD` | SMTP-пароль або пароль застосунку |
| `CONTACT_FROM` | Адреса відправника, надсилання від якої дозволяє ваш SMTP-сервіс |
| `CONTACT_TO` | Адреса власника, куди отримувати заявки |
| `CONTACT_TOKEN_SECRET` | Випадковий постійний секрет; обов'язковий для Vercel |

Секрет можна згенерувати на своєму комп'ютері командою:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Скопіюйте результат у налаштування сервера. Не вставляйте пароль або секрет
у HTML, публічний JSON, README чи GitHub. `.env` виключено з комітів і експорту.
У Vercel задайте значення для потрібного середовища; після зміни потрібне повторне
розгортання. На Node.js-сервері потрібен перезапуск.

### 3. Лише якщо сайт і обробник на різних доменах

На сервері обробника задайте:

```dotenv
CONTACT_ALLOWED_ORIGINS=https://www.your-site.example,https://your-site.example
```

Це точні адреси вашого сайту зі схемою `https://`, без шляху та завершального
слеша. Не використовуйте `*`. Додавайте лише адреси, які справді використовуєте.

У папці локального конструктора створіть `.env` і додайте **лише публічну адресу**:

```dotenv
CONTACT_FORM_ENDPOINT=https://your-mail-backend.example/api/contact
```

Перезапустіть конструктор, експортуйте сайт заново та завантажте свіжий ZIP на
хостинг. `START-EDITOR.cmd`, `npm run editor`, `npm run build` та `npm run export`
читають `.env`. В експорт потрапляє тільки адреса обробника в
`themes/contact-config.json`, не SMTP-паролі. Якщо сайт і обробник на одному
домені, залиште `CONTACT_FORM_ENDPOINT=/api/contact`.

### 4. Перевірте налаштовану пошту один раз

Відкрийте опубліковану сторінку `/feedback/`, заповніть ім'я, свою електронну
адресу й тестовий текст. Надішліть **одне** повідомлення, потім перевірте
`CONTACT_TO`, включно зі спамом. Текст «принято почтовым сервером» означає, що
SMTP-сервер прийняв повідомлення; це не підтвердження потрапляння у вхідні.

Якщо сталася помилка, введене залишається у формі. Перевірте SMTP-дані, дозволену
адресу відправника, журнали поштового сервісу та домени з пункту 3.
Не надсилайте паролі у повідомленнях про помилку.

Обробник не дозволяє відвідувачу обирати одержувача: адреса фіксована в
`CONTACT_TO`, а відповідь спрямовується на перевірений email відвідувача.
Є обмеження розміру, перевірка полів, origin, короткоживучий токен, поле-пастка
та ліміт частоти. Ліміт зберігається **в пам'яті одного процесу**; він не є
розподіленим антиспамом. Для великого трафіку потрібне окреме серверне
обмеження запитів. Автотести використовують імітацію SMTP й не надсилають
реальних листів.

винесені у спільні файли:

| Файл | Призначення |

Порядок стилів у `<head>` впливає на їхній пріоритет і збережений під час очищення.

збережених сторінок. Одноразові скрипти старих переробок прибрані; робочі команди
знаходяться в `scripts/`, перевірки — у `tests/`.

## Додатково: онлайн-редактор через GitHub і Vercel

Цей розділ не потрібен для локального конструктора та звичайного хостингу.
Онлайн-режим `/admin/` → **Увійти через GitHub** → **Опублікувати** записує зміни
у `KingInjiro/Tcg_site`, гілку `main`. Потрібен акаунт із правом запису.
Автооновлення Vercel працює, коли проєкт підключено до цього репозиторію.
На іншому хостингу потрібне власне розгортання; сам GitHub-коміт не оновлює його файли.

### Налаштування входу

`vercel.json` задає `npm run build`, каталог `dist` і заголовки адмінпанелі.
`api/auth.js` та `api/callback.js` виконуються як серверні функції Vercel.
Окремий сервер авторизації не потрібен.

1. У [GitHub → Settings → Developer settings → OAuth Apps](https://github.com/settings/developers)
   створіть **New OAuth App**.
2. Вкажіть фактичний основний домен сайту:
   - **Homepage URL:** `https://ВАШ-ДОМЕН`
   - **Authorization callback URL:** `https://ВАШ-ДОМЕН/api/callback`
3. Відкрийте створений OAuth App: поле **Client ID** уже є на його сторінці.
   У блоці **Client secrets** натисніть **Generate a new client secret**, підтвердьте
   GitHub-вхід і скопіюйте показаний секрет. Це дані застосунку, а не ваш пароль GitHub.
   `/api/callback` — адреса обробника в цьому проєкті; шукати окрему сторінку в GitHub не потрібно.
4. У Vercel → проєкт `tcg-site` → Settings → Environment Variables додайте:

   | Змінна | Значення |
   | --- | --- |
   | `CMS_ORIGIN` | `https://ВАШ-ДОМЕН` без `/admin` та інших шляхів |
   | `GITHUB_CLIENT_ID` | Client ID OAuth-застосунку |
   | `GITHUB_CLIENT_SECRET` | Client Secret OAuth-застосунку |

5. Застосуйте змінні до **Production** і виконайте нове розгортання.
6. Відкрийте `https://ВАШ-ДОМЕН/admin/`, натисніть вхід через GitHub і використайте
   обліковий запис із правом запису в `KingInjiro/Tcg_site`.

Секрет задається лише в налаштуваннях сервера, не в HTML
чи комітах. Запитується scope `public_repo`, оскільки цей репозиторій публічний.
GitHub OAuth із цим scope не обмежується одним публічним репозиторієм.
Якщо перевіряєте вхід на Preview-домені, використайте окремий OAuth App,
точний Preview-домен і відповідні Preview-змінні. Production OAuth-налаштування
не є універсальним входом для всіх Preview-адрес.

## Формат збереження та сумісність

Кожне збереження містить готовий HTML та дані блоків у
`.tcg-editor/<шлях-сторінки>.json`. Ці дані потрібні для повторного відкриття
конструктора; вони не копіюються у публічний `dist`. У локальному режимі HTML і JSON записуються у робочу папку.
У GitHub-режимі вони потрапляють в один коміт через GitHub Git Data API; оновлення гілки не використовує force.
Якщо HTML змінено іншим інструментом, редактор перевіряє його SHA-256 і імпортує
актуальний HTML замість застарілого проєкту.

Саме відкриття сторінки не змінює файл. Після візуального редагування GrapesJS
нормалізує HTML і записує свої стилі; побайтова тотожність старого HTML не обіцяється.
Зберігаються метадані голови документа, шляхи зображень, посилання та службові вставки.
Залишено один візуальний редактор на `/admin/`. Стару резервну Decap-адмінку,
її окремий локальний сервер і залежності прибрано; `/admin/legacy.html`
перенаправляє до основного конструктора. Це не змінює збережені сторінки,
чернетки або налаштування GitHub-входу. Перелік сторінок визначається автоматично.

### Відновлені файли та зображення

Редактор перевіряє вміст файлів, а не лише розширення `.html`. Двійкові документи,
текст із пошкодженим кодуванням і збережені відповіді Apache «404 Not Found»
не пропонуються як сторінки та не потрапляють у публічну збірку. Перевірка також
виконується перед імпортом і публікацією. Нові справні HTML-сторінки, зокрема
в `Docs/` та `ListPage/`, знаходяться автоматично.

Під час перевірки 24.09.2026 відновлено оригінали з `http://www.tcg.com.ua/`:

- `PCTarf.files/image002.gif`, `image004.gif`, `image006.gif` — ілюстрації тарифів;
- `images/Help.jpg` — ілюстрація на сторінці комплексного обслуговування;
- `Docs/Sno_for_Buh_ua.ert` — документ 1С, який помилково був збережений як HTML.

Логотип `images/logo.gif` відновлено зі справної вбудованої копії у `TEconom.html`.
Виправлено адреси кнопок у статтях і кнопок «Вверх». Відсутні картинки маркерів
списку замінено символами, кнопку «Статьи о нас» та недоступний банер META —
текстовими посиланнями. HTTP-банер MyTOP у `noscript` також замінено текстовим
посиланням; скрипт лічильника збережено. Кодування `prod01.html` та службової сторінки FrontPage
узгоджено з UTF-8; відновлено символ ©.

Старе посилання `/Docs/Sno_for_Buh_ua.html` перенаправляє на завантаження `.ert`.
Пошкоджені імпортовані HTML-файли залишені в репозиторії для історії, але недоступні
як публічні сторінки. Архіви `Docs/rp*.zip` на старому сайті повертають 404;
збережені замість них сторінки помилок не містять звітів. Для відновлення цих
архівів потрібні справжні ZIP-файли. Документ 1С збережено без змін його вмісту;
перевірка завантаження не означає перевірку виконання в 1С.

OAuth-налаштування залишаються тими самими: `/api/auth`, `/api/callback` і три змінні
з розділу налаштування входу. Токен GitHub зберігається лише в пам’яті вкладки. Після перезавантаження
потрібно знову натиснути кнопку входу. Збережений JSON не містить токенів або секретів.

Локальний Express-сервер у production-режимі потребує оновлення коду та перезапуску
після публікації через GitHub.

## Додатково: запуск онлайн-редактора на Node.js сервері

Для статичного ZIP цей розділ не потрібен. Не запускайте локальний режим `--dev`
або `npm run editor` як публічний сервер: він призначений лише для вашого комп’ютера.

Скопіюйте `.env.example` у `.env`, задайте ті самі три OAuth-змінні та запустіть:

```sh
npm ci
npm start
```

`npm start` створює `dist` перед запуском. Порт — `PORT` або `3000`.
HTTPS має завершуватися на вашому reverse proxy. Для локального OAuth-тесту
можна задати `CMS_ORIGIN=http://localhost:3000` та відповідний callback URL
у окремому тестовому OAuth App.

## Перевірки та діагностика

```sh
npm test
npm run build
npm run export
```

`npm run export` створює ZIP з уже збережених файлів у `exports`, не змінюючи `dist`.
Він не може прочитати незбережені правки з відкритого браузера. Експорт обмежений
64 МБ вихідного сайту; при перевищенні повертається помилка, файли не пропускаються мовчки.

Браузерна перевірка створює ізольовану тимчасову копію сайту й не змінює
робочі сторінки або GitHub. Після встановлення Chromium:

```sh
npx playwright install chromium
npm run test:browser
npm run test:content
npm run test:calculators
```

Перша команда перевіряє імпорт наявних сторінок, фактичне декодування картинок
у конструкторі, зміну тексту, перетягування блоків, нові сторінки, фото, копіювання,
відновлення чернеток, конфлікт збереження та експорт із незбереженими правками.
Архів перевіряється після розпакування на звичайному статичному сервері, включно
з новою сторінкою, фото та старими `.htm`-адресами. Друга відкриває сторінки готового `dist`
на статичному сервері без виправлення регістру адрес: перевіряє UTF-8, завантаження
локальних ресурсів і декодування кожного файлу зображення в Chromium.
Третя перевіряє розрахунки обох калькуляторів, помилкове введення, відмову
при недоступних або застарілих курсах та повторне завантаження. Відповіді НБУ
в цих тестах контрольовані; це не перевірка доступності живого API.
Зовнішні лічильники та рекламні сервіси не входять до цієї автоматичної перевірки.

Додаткові перевірки технічного оновлення:

```sh
# HTML Validator потребує Java 17 або новішу; це інструмент розробника, не сайту.
npm run test:html
npm run test:links
npm run test:functionality
npm run test:accessibility
```

Для Firefox/WebKit спочатку встановіть відповідні браузери Playwright і запустіть
`test:functionality` зі змінною `TCG_TEST_BROWSER=firefox` або `webkit`.
Структурна перевірка доступності окремо повідомляє зауваження до незмінних кольорів
та оформлення посилань; зелений результат не означає повну відповідність WCAG.

Актуальне порівняння вигляду використовує еталон після PR #17
(`56373e97ce218fbd390219e299538b70f95fb26c`):

```sh
TCG_BASELINE_DIR=/path/to/baseline-checkout npm run test:preservation
```

Воно порівнює видимі тексти, шрифти, кольори, розташування тексту та зображень на
всіх 51 сторінці при 1440 і 390 пікселях. Виняток — геометрія форми `price1C`:
під наявними підписами відновлено відсутні поля й кнопки. Динамічні зовнішні
вставки не виконуються під час порівняння. GitHub Actions запускає ці перевірки
для PR у `main`, але не публікує сайт і не надсилає листів.

Нижче залишено попередній тест для відтворення окремого етапу очищення до зміни
семантичної структури; для цього PR використовуйте `test:preservation`.

Порівняння оформлення попереднього етапу з його еталоном:

```sh
TCG_BASELINE_DIR=/path/to/baseline-checkout npm run test:appearance
```

Для очищення коду еталон — коміт `d2915aa82bafd7b5a3a6e1a51772cde74b3d471e` (після PR #15).
Перевірка порівнює тексти, посилання, адреси зображень, шрифти, кольори, рамки й координати елементів усіх 51 сторінки
при ширині 1440 та 390 пікселів (допуск округлення — 1 піксель). Зовнішні картинки
замінені однаковими тестовими відповідями. Окремо перевіряються наведення та фокус
клавіатури на наявних GIF-кнопках, реєстрація офлайн-кешу та перенаправлення старих
адрес зі збереженням параметрів і фрагмента `#...`.
За потреби `TCG_BROWSER_EXECUTABLE` задає шлях до встановленого Chromium.
Модульні набори запускаються послідовно, оскільки використовують спільний `dist`.

Тести перевіряють OAuth state/PKCE, відмову без налаштувань і прав запису,
безпечну передачу результату до редактора, атомарний GitHub-коміт, конфлікти змін,
обмеження шляхів, захист локального API та відсутність серверних файлів у публічній збірці.
Тести OAuth використовують імітацію відповідей GitHub; вони не замінюють
перевірку реального входу після налаштування OAuth App.

- **«Вхід ще не налаштовано»**: перевірте три змінні та повторне розгортання.
- **Сеанс входу недійсний**: відкрийте CMS на домені з `CMS_ORIGIN` та почніть
  вхід повторно; дозвольте cookies й спливне вікно для цього сайту.
- **Немає права редагувати**: перевірте GitHub-акаунт і його доступ до репозиторію.
- **Зміни опубліковані, але їх ще немає на сайті**: перевірте коміт у `main`
  та завершення пов'язаного deployment у Vercel.
